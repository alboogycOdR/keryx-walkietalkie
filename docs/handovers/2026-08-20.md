## Traps discovered
- **`sync-manifest.json` in DEVDEPARTMENT must list every new script AND its test file** in `framework_owned`, or `sync_from_pack.py` silently won't propagate them to downstream projects — caught by that repo's own `test_sync_from_pack.py::TestManifestPathsAreLiteral::test_every_shipped_test_file_is_registered`. If you add any new pack-owned file there in future, add it to the manifest in the same commit.
- **`SendUserFile` has a ~30MB delivery limit.** `--debug` Flutter builds (200MB+) blow way past it; `--release --split-per-abi` builds are small enough for the `armeabi-v7a` variant (~26MB) to fit directly, but `arm64-v8a` (~35MB) still needs the `ship-to-telegram` skill (Gofile upload + Telegram link) instead.
- **Worktree "Access is denied" / "being used by another process" on `Remove-Item -Recurse -Force`** is NOT a lingering test-run file handle (that was an earlier wrong guess) — it's leftover `-NoExit` PowerShell console windows spawned by `dispatch.ps1`'s runner scripts (`.devteam/launch/<Builder>-<timestamp>.run.ps1`), which never close after the inner `claude` session ends and keep the worktree as their working directory. Find and kill the specific process via `Get-CimInstance Win32_Process | Where CommandLine -match 'wt-<builder>'` before retrying removal. A real fix (drop `-NoExit`, or have `dispatch.ps1` self-clean prior runner processes on next launch) has not been implemented yet — this is still a manual workaround.
- **Independent test-run subagent counts sometimes differ from a builder's own `Test_Evidence` count by exactly 1** (seen three times this session: 22 vs 21, 22 vs 21, 17 vs 16) — this is a JSON/compact-reporter artifact (likely a synthetic suite-loading pseudo-entry), not a real defect, each time confirmed by cross-checking a static `grep -c "test("` on the committed file plus Flutter's own literal `+N: All tests passed!` summary line. Don't charge a builder rework for this without cross-checking a second way first.
- **The Telegram `needs_review` hook does not fire from `supervisor.py`'s own P0/P1/P2 path** — it's a separate mechanism entirely, wired into `plan_commit.ps1`/`.sh` directly. Don't go looking for it in `supervisor.py`.
